# dsh-workplan 卡住问题复盘、诊断与 1.3.4 修复

> 复盘对象：`<repo>`（1.2.1 及更早版本的运行记录）
> 修复版本：**1.3.0 → 1.3.1 → 1.3.2 → 1.3.3 → 1.3.4**
> 复盘时间：2026-10-26
> 证据性质：本文件所有数字均来自本机可读的会话存档或可重跑测试；标注「未验证」的条目没有证据支撑。

## 1. 结论摘要

「卡住」不是一种故障，而是**一条失效链**：

1. 单个子 Agent 停住 → 被**固定 300 秒墙钟**判死（`CHILD_TIMEOUT_MS = 300000`，不看是否还在产出）；
2. 它的下游全部被标成「上游子任务受阻」→ 整份计划进入 `blocked`；
3. 再次调用 `dsh_workplan_dispatch` 时，所有子任务都是 `blocked`，可调度集合为空 → 派发器**一个子 Agent 都没跑就返回 `ok: true`**；
4. 模型看到 `ok: true` 以为已恢复，于是永远等下去；用户看到的则是「完成 0/N」。

历史证据里，**76% 的受阻子任务是一次失败引发的级联**（112/148）。所以真正的放大器不是 300 秒本身，而是第 3 步的「假成功」——它把一次可恢复的失败变成了死局。

1.3.0 的修复分三层：**判定更准**（无进展才算卡住）、**恢复可达**（受阻可续跑、额度用尽时明确交还主 Agent）、**不可能静默卡死**（取消一定能生效、陈旧派发会超时返回、错误永远可读）。

### 2.2 判定口径

满足任一条件即记为「卡住事件」：

- 派发返回 `ok: true` 但 `stats.done == 0` 且 `stats.blocked > 0`（假成功）；
- 出现 `子任务 T? 超时（300000ms）` 错误串；
- 计划长期停在 `blocked` 且无后续派发；
- 用户侧想停止却收到 `计划正在执行，不能取消`；
- 错误串不可读（`[object Object]`）导致无法定位。

## 3. 历史证据

### 3.1 派发结果分布（去重后 23 次派发）

| 结果 | 次数 | 说明 |
| --- | --- | --- |
| 全部完成 | 6 | 同一版本、同一环境下可以跑完，**说明不是全局性环境故障** |
| 完成 0 个且至少 1 个受阻 | **11** | 高危：表面 `ok: true`，实际零产出 |
| 至少 1 个受阻（含上项） | 17 | 74% |
| 计划最大子任务数 | 13 | 超过 5 并发，会排队 |

### 3.2 148 条受阻子任务的直接原因

| 原因 | 条数 | 占比 |
| --- | --- | --- |
| 级联：`上游子任务受阻：T?` | **113** | **76%** |
| 超时（其中 5 条明写 `300000ms`，17 条为旧版无毫秒文案） | 22 | 15% |
| `调度次数异常`（派发循环保护触发） | 12 | 8% |
| `[object Object]`（错误不可读） | 1 | <1% |

另有 1 条 `执行已取消` 记录、1 条用户在计划执行中尝试取消被拒的痕迹。

补充说明（避免把已修的问题再算一次）：那 12 条 `调度次数异常` 出现在 2026-10-25 的旧计划里，对应缺陷是调度器把 `readySubtasks()` 返回对象的 `id` 当成了 `subtaskId`，导致每个可调度项都被跳过、循环空转到保护上限。当前源码已修复（`src/runtime.ts` 派发循环内有注释说明），并有回归测试 `dispatch runs real DAG subtasks and does not hit the loop guard`。这些历史记录的具体插件版本号**未验证**。

**读法**：把 113 条级联剥掉，真正独立的失败证据只有 22 条超时 + 12 条循环 + 1 条不可读错误。也就是说，**一次失败平均拖垮约 5 个子任务**——这正是「卡住」在用户视角里的样子。

## 4. 根因

| 编号 | 根因 | 代码位置（1.2.1） | 为什么会导致「卡住」 |
| --- | --- | --- | --- |
| R1 | 固定的墙钟上限，且不区分「还在产出」和「已经停住」 | `CHILD_TIMEOUT_MS = 300000` | 慢但健康的子 Agent 被一律杀头；用户无法配置 |
| R2 | 一个子任务受阻 → 所有下游标为受阻 | 派发器依赖判定 | 放大 5 倍（112/148），且不可逆 |
| R3 | **受阻计划重新派发时「假成功」** | `readySubtasks()` 对全 `blocked` 返回空 → `ok: true` | 模型以为已恢复，永远等待；无任何提示说明「什么都没跑」 |
| R4 | 运行中的计划拒绝取消 | `cancelPlan` 抛 `PLAN_RUNNING` | 想停也停不下来；唯一出路是杀进程 |
| R5 | `dispatchPromise` 永挂 → 永远回答 `already running` | `dispatchTool` 只 `await` 不设上限 | 一次僵死会污染后续所有调用的入口 |
| R6 | 错误用 `String(error)` 渲染 | `pushRecordError` / 子任务 error | 落盘成 `[object Object]`，事后无法诊断 |
| R7 | 子 Agent 提示词直接解引用 `taskUnderstanding` / `contradictions` | `buildChildPrompt` | 重建或旧版计划缺字段时，每个子 Agent 瞬间失败 → 整份计划受阻（1.3.0 开发期由测试实际触发） |
| R8 | 续跑后不重写结果消息；构建脚本漏拷新模块 | `record.resultWritten`、`package.json` build | 刷新页面看到旧的受阻快照；新模块会让插件加载失败（1.3.0 引入时必须同步修） |
| R9 | 工具超时硬编码 `1220000`，与计划预算不联动 | `host.ts` dispatch 工具 `timeoutMs` | 提高了计划预算后，工具仍会在中途被杀 |

环境因素（网络、模型）**不能**解释证据：同一时间段有 6 次全部完成的派发；失败时长精确等于常数。

## 5. 修复映射（1.3.0）

| 根因 | 修复 | 位置 |
| --- | --- | --- |
| R1 | 拆成「无进展窗口（默认 300s）」+「绝对上限（默认 900s）」；只有会话日志停止增长才判 `stalled`，触到上限判 `exhausted`；`stalled` 自动换新子 Agent 重试一次，`exhausted` 不重试 | `src/watchdog.ts:37`（`pickTimeoutReason`）、`src/watchdog.ts:121`（`createProgressWatchdog`）、`src/runtime.ts:341`/`:351`（`normaliseChildTimeout`/`normaliseIdleTimeout`） |
| R2 | 受阻只影响自身，恢复由续跑承担：`resetBlockedStatuses` 只重置 `blocked`/`in_progress`，`done` 永不重跑 | `src/plan.ts:1158` |
| R3 | `canResumePlan` 判定：仅 `blocked` 可续跑，`cancelled` 永不自动续跑，额度默认 2（0–5 可配）；额度耗尽返回 `ok: false` + `hint` 要求主 Agent 直接接手 | `src/plan.ts:1187`、`src/runtime.ts:652` 起 |
| R4 | 取消会中止在途派发，返回 `abortedRunning: true`，计划进入 `cancelled`，在途结果仍写 durable 消息 | `src/runtime.ts:1116`、`src/runtime.ts:1218` |
| R5 | 超过「计划预算 + 120s」仍未返回 → `ok: false`、`stale: true`、`hint` 提示直接接手 | `src/runtime.ts:1165` |
| R6 | `describeError()` 统一渲染 Error / 字符串 / 嵌套对象 / Envelope 文本；错误列表与子任务 error 全部走它 | `src/watchdog.ts:64` |
| R7 | 提示词对 `taskUnderstanding`、`contradictions`、`method`、`inputs`、`outputs`、`acceptance` 全部做防御性读取 | `src/plan.ts:1222` |
| R8 | 续跑清除 `resultWritten`（`src/runtime.ts:659`）；build 脚本补 `dist/watchdog.js` | `src/runtime.ts`、`package.json` |
| R9 | 工具超时 = `limits.totalTimeoutMs + 20000`；四项阈值可用配置键或环境变量覆盖 | `src/host.ts:213`、`src/host.ts:228` |

### 5.1 新增可配置项

| 配置键 | 环境变量 | 默认 | 范围 |
| --- | --- | --- | --- |
| `childTimeoutMs` | `DSH_WORKPLAN_CHILD_TIMEOUT_MS` | 900000 | 1000–1800000 |
| `idleTimeoutMs` | `DSH_WORKPLAN_IDLE_TIMEOUT_MS` | 300000 | 1000–900000 |
| `totalTimeoutMs` | `DSH_WORKPLAN_TOTAL_TIMEOUT_MS` | 1200000 | ≥ 60000 |
| `maxResumes` | `DSH_WORKPLAN_MAX_RESUMES` | 2 | 0–5 |

### 5.2 不变量（修复后必须始终成立）

1. 子 Agent 只要还在写会话日志，就不会因为「慢」被杀死。
2. `blocked` 计划再次派发时，要么真的跑起来，要么 `ok: false` 并给出原因——不存在「`ok: true` 但零产出」。
3. 任何派发都有终点：完成、受阻、取消、或超时返回，四者之一。
4. 错误文本永远可读，不含 `[object Object]`。
5. 取消命令在任何阶段都生效。

## 7. 残余风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 子 Agent「缓慢但持续产出」会耗尽 900s 上限 | 该子任务受阻，下游受阻 | 上限可配；续跑保留已完成部分；`hint` 要求主 Agent 接手 |
| 续跑额度默认 2 次仍可能不够 | 第三次起必须人工接手 | 可用 `DSH_WORKPLAN_MAX_RESUMES` 调至 5；结果消息明确说明 |
| 计划重建依赖 durable 消息 | 消息被裁剪则续跑信息丢失 | 消息与计划同源落盘，不依赖内存态 |
| 未接入集中监控 | 只能靠下次复盘扫描 | 建议按 §8.3 定期扫描 `子任务 … 超时`、`readySubtasks 为空`、`[object Object]` |

### 8.3 每次复盘的重扫命令（防止复发看不见）

```bash
# 统计含插件记录的会话：去重后的派发数、假成功（ok 但零完成）数
python3 - <<'SCAN'
import json,os,re,subprocess
ROOT=os.path.expanduser('~/.dsh/sessions'); rows=[]
for dp,_,fns in os.walk(ROOT):
    for fn in fns:
        if fn!='session.v4.jsonl.zstd': continue
        p=os.path.join(dp,fn)
        txt=subprocess.run(['zstd','-dc',p],capture_output=True).stdout.decode('utf-8','replace')
        if 'DSH-WORKPLAN-RESULT:BEGIN' not in txt: continue
        for line in txt.splitlines():
            try: e=json.loads(line)
            except: continue
            d=e.get('data') or {}; m=d.get('message') or d
            t=''.join(c.get('text','') for c in (m.get('content') or []) if isinstance(c,dict))
            mm=re.search(r'RESULT:BEGIN -->\s*(.*?)\s*<!-- DSH-WORKPLAN-RESULT:END', t, re.S)
            if not mm: continue
            try: pay=json.loads(mm.group(1))
            except: continue
            rows.append(pay)
uniq={(r.get('planId'),r.get('dispatchedAt')):r for r in rows}
u=list(uniq.values())
fake=[r for r in u if (r.get('stats') or {}).get('done')==0 and (r.get('stats') or {}).get('blocked',0)>0]
print('原始载荷',len(rows),'去重派发',len(u),'假成功(零完成)',len(fake))
for r in fake: print(' ',r.get('dispatchedAt'),r.get('planId'),r.get('stats'))
SCAN
```

## A.2 本轮暴露的新缺陷：计划总预算把正常慢计划判成失败

- 时间线：18:53:18 派发 → T1 用掉 840 s、T2 用掉 137 s → 19:13:18 到达 `TOTAL_TIMEOUT_MS = 1200000`（20 分钟）→ 正在跑的 T3 被中止并记为「总执行超时」→ T4–T9 以「上游子任务受阻：T3」级联受阻。
- 为什么是缺陷（而不是配置问题）：
  1. 预算到点与子任务失败共用同一套「受阻」语义，面板再次显示「0~2/N 做好了、N 卡住了」，正是用户反复投诉的症状；
