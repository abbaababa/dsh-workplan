# 决策：澄清闸门与自动派发的边界（2026-11-04）

## 1. 用户拍板

> 「此外，DSH_WORKPLAN_AUTO_DISPATCH 改为在"信息不足"类上拦截，其它全部按你推荐的去做」
> —— 2026-11-04 20:53，用户原文

含义（按原文，不引申）：

1. **自动派发本身不改**：计划生成后照旧自动开跑，不要求用户每次点确认。
2. **只有一类要拦**：任务信息不足（缺关键输入、缺指代、缺标的、缺界面对象）时，不要拆计划、不要派发，改为向用户提问。
3. 其余三项（①指代放宽 ②澄清提问 ④法务召回）按主 Agent 的建议执行。

## 2. 为什么拦在「规划之前」而不是「派发之前」

MS2 的 20 条是整会话任务：被测 agent 收到原文后会自己决定「先派发计划」。
如果拦在派发这一步，计划已经生成、计划列表里已经出现一个基于猜测的 planId，
用户看到的仍是「已经开工，只是没开跑」。拦在规划之前则连计划都不产生——
没有 planId，也就没有可被误派发的对象。

## 3. 判定规则（可复算，不靠感觉）

| 规则 | 触发条件 | 对应的 MS2 用例 |
|---|---|---|
| C1 裸表态 | 句首是「同意/赞成/按你说的…」，且带一个任务里没定义的编号或整句 ≤24 字 | T05-04「…同意移入」 |
| C2 悬空内部编号 | 出现 `R-W5-01`/`W5`/`T4 草稿` 这类编号，且任务与最近对话里都没定义 | T05-09「按 T4 草稿开始续做」 |
| C3 预测类无标的 | 出现 预测/预判/走势/涨跌/行情，且原文与上下文都没有 6 位代码、字母+数字、引号名称 | T05-20「准确预测11月全月详细、具体走势」 |
| C4 界面改动无对象 | 出现 折叠/展开/按钮/显示/布局…，且原文与上下文都没有 左侧栏/面板/截图/红圈… | T05-13「显示内容希望可折叠」 |

「上下文也算」是刻意的：上一轮说过「截图红圈处的分步进度」，本轮「把它改成默认收起」
是正常追问，不该被拦（`tests/plan-anchor.test.ts` 的 strict 用例钉住了这一点）。
