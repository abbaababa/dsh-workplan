# 部门职责与交接约定

> 配套文档：[协作契约（唯一入口）](collaboration.md)。本文把「12 个部门分别负责什么、交接时给什么、什么算交清楚」讲透；机制细节与代码事实一律以协作契约为准。

## 0. 先厘清：部门是什么，不是什么

- **是职责标签。** `src/plan.ts#DEPARTMENTS` 里的 12 个 key 决定子任务的提示词、面板分组与统计口径。
- **不是组织架构。** 1.7.0 仍没有部门负责人、部门队列、部门内串行、部门预算；同一部门的两个子任务也可以并行。
- **不是通信通道。** 部门之间不能直接对话；跨部门信息经主 Agent 转达、落到工作区文件，或写进子 Agent 回传的 `needs` 由结果消息汇总（见协作契约 §5.3）。
- **不代表权限。** 任何部门都不能派发、改判、取消计划；这些只有主 Agent 能做。

选部门的唯一标准：**这件工作主要由谁的专业判断负责，就选谁。** 拿不准时按「产物归谁验收」选，而不是按「谁顺手动一下」选。

## 1. 十二个部门一览

| key | 中文 / English | 典型工作 | 验收时最该看什么 | 常见下游 |
|---|---|---|---|---|
| `engineering` | 工程研发 / Engineering | 写代码、改架构、修缺陷、写脚本与测试 | 能构建、能运行、有测试证据；改动范围与文件清单 | `qa`、`security`、`devops`、`writing` |
| `research` | 研究分析 / Research | 调研、对比方案、查文档/资料、给出事实与来源 | 结论有来源、区分「已验证」与「推测」、说明时效 | `product`、`design`、`engineering`、`writing` |
| `design` | 设计 / Design | 交互、视觉、信息结构、文案语气、可用性 | 状态齐全（空/错/加载/成功）、边界与无障碍、可交付稿 | `engineering`、`product`、`writing` |
| `product` | 产品 / Product | 需求拆解、范围与优先级、验收口径、取舍 | 目标与非目标清楚、验收可判定、依赖与风险写明 | 全部 |
| `data` | 数据 / Data | 取数、清洗、指标定义、分析、报表 | 口径与时间窗、样本量、可复现的查询/脚本 | `product`、`engineering`、`finance`、`operations` |
| `qa` | 质量验证 / QA | 测试设计、回归、验收执行、缺陷复现 | 用例覆盖改动点、复现步骤、通过/失败证据 | `engineering`、`product` |
| `security` | 安全 / Security | 威胁建模、权限与密钥、依赖与供应链、审计 | 攻击面与缓解、密钥不落库、最小权限 | `engineering`、`devops`、`legal` |
| `devops` | 运维 / DevOps | CI/CD、发布、回滚、监控、环境与配置 | 可重复执行、回滚路径、观测点、变更影响 | `engineering`、`qa`、`operations` |
| `writing` | 文档写作 / Writing | README、指南、CHANGELOG、对外说明、协作规范 | 与实现一致、步骤可照做、覆盖改动点 | 全部（对外交付） |
| `operations` | 运营 / Operations | 流程、活动、客服口径、日常运转 | 责任人与时限、异常处理、可执行清单 | `product`、`finance`、`writing` |
| `legal` | 法务合规 / Legal | 条款、隐私、许可、合规风险 | 适用法域与版本、风险等级、需人工复核项 | `product`、`security`、`writing` |
| `finance` | 财务 / Finance | 成本、预算、计价、对账 | 口径与币种、假设、区间与敏感性 | `product`、`operations`、`writing` |

> 部门 key 必须与 `src/plan.ts#DEPARTMENTS` 完全一致；新增部门要同时改代码、本文与协作契约 §1。**不要**在计划里写自由文本部门名。

## 2. 所有部门共用的交接契约

### 2.1 上游必须交出的四样东西

一个子任务要能被下游直接接手，它的结果摘要（≤3000 字，超出被截断）必须包含：

1. **做了什么**：一句话结论 + 关键决定；
2. **产物在哪**：绝对路径（文件/目录）或可访问 URL；没有产物就写「无文件产物」；
3. **怎么用/怎么验**：下游复现或验收的最短命令/步骤；
4. **边界与遗留**：没做什么、已知风险、需要谁确认。

只写「已完成」「没问题」不算交清楚——下游拿不到任何可执行信息。

### 2.2 下游必须回什么

- 接收时：确认自己拿到的是哪个版本/哪份文件（路径或摘要里的标识）；
- 完成时：按 §2.1 回四样东西；
- 受阻时：**第一行** `BLOCKED: 原因`，正文写清卡在哪、试过什么、需要谁做什么；
- 需要别的部门配合时：写「需要主 Agent 转达：…」，**不要**假设对方能看到你的对话。

### 2.3 交接的三种形态

| 形态 | 何时用 | 机制 | 注意 |
|---|---|---|---|
| 串联 | 下游依赖上游结论/产物 | 计划里写 `dependsOn: ["T1"]` | 只有上游 `done` 下游才开跑；下游只看到上游摘要，**务必把路径写进摘要** |
| 并行对齐 | 两件事可同时做，但接口要对齐 | 同一阶段、无依赖 | 彼此看不到对方；接口必须由计划或主 Agent 事先写死 |
| 升级转达 | 需要另一个部门补信息/做决定 | 主 Agent 用 `update` 的 `note`/`evidence` 记录，或在下一轮对话补充 | 1.7.0 的 `needs` 会自动汇总成「跨部门待转达」，但仍由主 Agent 执行转达 |

### 2.4 交接自检清单（交接前逐条过）

- [ ] 结论在第一段，路径是绝对路径，且文件真的存在；
- [ ] 验收标准逐条有「通过 / 未通过 / 未验证」，没有把「没测」写成「通过」；
- [ ] 下游不需要读我的对话就能开始；
- [ ] 失败信号在第一行，且是 `BLOCKED:` 开头；
- [ ] 没有替别的部门做决定，也没有隐瞒已知风险；
- [ ] 没有编造命令输出、文件或外部事实。

## 3. 逐部门交接要点

### 3.1 工程研发（engineering）

- **交付**：改动文件清单、构建/测试命令与结果、回滚方式；涉及接口时给调用示例。
- **交接给 QA**：改动点 → 受影响路径 → 建议用例；不要只给「跑一下测试」。
- **交接给运维**：配置项、迁移步骤、是否需要重启、观测指标。
- **禁区**：不得擅自发布、改生产配置、装全局依赖；这些需要主 Agent/用户授权。

### 3.2 研究分析（research）

- **交付**：结论、证据（链接/出处/日期）、反例与不确定性；区分「官方文档」与「二手说法」。
- **交接给产品/设计**：把发现翻译成「对范围/优先级的影响」，而不是堆资料。
- **禁区**：不得把搜索摘要当原文；无法访问的来源标「未验证」。

### 3.3 设计（design）

- **交付**：可打开的稿/原型或规格说明；覆盖空态、错误、加载、成功与极端内容。
- **交接给工程**：尺寸/间距/颜色 token、交互状态、文案终稿；避免「看着办」。
- **交接给产品**：取舍理由与可用性风险。

### 3.4 产品（product）

- **交付**：目标、非目标、验收口径、优先级、依赖与风险；有争议时给推荐方案与理由。
- **交接给所有人**：一份可判定的「什么算完成」，避免各部门各自解释。
- **禁区**：不得替用户拍板不可逆决定；需明确列出待确认项。

### 3.5 数据（data）

- **交付**：指标定义、时间窗、过滤条件、查询/脚本、结果与样本量；数字要给口径。
- **交接给工程/财务**：可复现的最小脚本或 SQL，不只给截图。
- **禁区**：不得混用不同口径的分子分母；不得隐去缺失值处理。

### 3.6 质量验证（qa）

- **交付**：用例清单（对应验收标准）、执行结果、失败复现步骤、环境与版本。
- **交接给工程**：一个失败一条记录，含期望/实际/日志；不要合并成「都不行」。
- **禁区**：不得把「未执行」写成「通过」；不得只测 happy path。

### 3.7 安全（security）

- **交付**：威胁与攻击面、缓解措施、剩余风险、需人工复核项；密钥/权限的最小化说明。
- **交接给工程/运维**：可执行的加固清单与验证方法（命令/检查点）。
- **禁区**：不得在文档、日志、摘要里写明文密钥；不得声称「绝对安全」。

### 3.8 运维（devops）

- **交付**：可重复的发布/回滚步骤、环境差异、观测点、变更窗口与影响面。
- **交接给工程/QA**：失败时看哪里、如何回滚、如何确认恢复。
- **禁区**：不得在未授权时改生产；不得省略回滚路径。

### 3.9 文档写作（writing）

- **交付**：更新后的文档清单、覆盖矩阵（改动点 → 文档位置）、与代码一致性核对方法。
- **交接给发布**：安装步骤必须能照做；版本号/链接/命令要可复制；未实现的能力必须标注。
- **禁区**：不得把「计划中」写成「已发布」；不得写行号（用符号引用）。

### 3.10 运营（operations）

- **交付**：流程步骤、责任人、时限、异常处理与升级路径；对外口径要统一。
- **交接给产品/财务**：可执行清单与成本/人力假设。
- **禁区**：不得承诺未确认的资源或时限。

### 3.11 法务合规（legal）

- **交付**：适用法域、条款/许可版本、风险等级、需律师复核项；引用要给出处。
- **交接给产品/安全/文档**：把结论落成「能做/不能做/需改法」的清单。
- **禁区**：不得把一般性说明当成正式法律意见；不确定必须标注。

### 3.12 财务（finance）

- **交付**：口径、币种、假设、区间与敏感性；对账差异要解释。
- **交接给产品/运营**：成本结构与可选方案对比，而不是单一数字。
- **禁区**：不得混淆一次性投入与经常性成本；不得省略假设。

## 4. 典型跨部门链路（照抄即可）

| 场景 | 推荐链路 | 关键交接物 |
|---|---|---|
| 新功能从想法到上线 | product → design → engineering → qa → security → devops → writing | 验收口径 → 设计稿 → 改动清单/测试 → 用例结果 → 加固清单 → 发布/回滚步骤 → 对外说明 |
| 线上问题定位 | qa/operations → engineering → data → writing | 复现步骤/日志 → 根因与修复 → 影响面数据 → 事故说明 |
| 对外发布 | engineering → qa → security → legal → writing → operations | 构建产物 → 回归结果 → 合规结论 → 发布物料 → 客服口径 |
| 数据驱动决策 | data → product → finance → writing | 口径与结论 → 取舍建议 → 成本影响 → 决策记录 |

链路只是建议：**真正决定先后的是计划里的 `dependsOn`**，不是这张表。

## 5. 冲突、受阻与升级

1. **两个部门结论冲突**：不要私下裁决。各自给出证据与适用条件，由主 Agent 汇总，必要时请用户拍板。
2. **接口对不上**：先确认版本/路径，再判定是上游交不清还是下游理解错；把结论写进 `update` 的 note，避免下一轮重犯。
3. **上游受阻**：下游会被级联标记 `blocked`，错误文案是「上游子任务受阻：T1」。先修上游，再续跑；不要在受阻状态下硬写完成。
4. **需要越权动作**（发布、装服务、改生产、对外发信）：写「需要主 Agent/用户执行」，然后停下，不要等待或空转。
5. **发现计划本身错了**：向主 Agent 说明错在哪、建议怎么改；计划由主 Agent 更新，子 Agent 不自行改计划。

## 6. 1.7.0 对交接的影响（目标，未发布）

| 变化 | 对部门交接的意义 |
|---|---|
| 子 Agent 末尾证据块（`status / acceptance / artifacts / needs`） | 「交清楚」从口头约定变成可解析字段；`artifacts` 会做存在性检查 |
| `needs` 清单 | 跨部门依赖可被主 Agent 汇总转达，减少「等对方」 |
| 兄弟任务只读一览 | 并行部门能看到彼此的目标与边界（仍不能直连） |
| 运行中写保护 + `revision` | 主 Agent 改判不会被子任务结束覆盖；交接结论更稳定 |

在这些能力发布前，**按本文 §2 的手写约定执行**；发布后以协作契约 §9 的实际状态为准。
