# dsh-workplan 3.2.9 发布说明

发布日期：2026-11-25

一句话：这一版让插件在“该拆子代理时拆、该由主上下文想清楚时别乱拆”，并且把专家真正需要的那一小块上下文精准送到专家手里；同时把“哪些信息必须一字不改、哪些可以压缩”变成代码规则，减少重复付费，又不丢关键数字和路径。

## 一、先说明白：这一版没有做什么

用户提出的第 4 项（KV Cache 层面记忆共享）和第 5 项（模型内软 Token 压缩）有一个硬边界：**dsh-workplan 是 DSH 的插件，只能给模型发文本请求，拿不到模型内部的 KV 张量，也不能生成真正的 soft token。** DSH 的 `llm/stream` 只提供文本/工具调用/usage 这些字段，主循环请求还是深冻结的，插件不能改写。

所以这一版对第 4、5 项做的是**插件级等价实现**，不是“模型内 KV 共享/软 token”：

- 第 4 项 = 结构化 Latent Brief（按任务挑记忆、保留精确引用、稳定前缀、复用编译缓存）+ 供应商真实返回的 `cacheRead/cacheWrite` 计量；
- 第 5 项 = 硬事实逐字保留（数字/路径/哈希/编号/命令/验收编号）+ 软内容压成摘要 + 省略项保留 ref。

字面实现需要改 DSH 内核并自建本地推理（加载模型权重、改 attention/KV 接口），已另附设计文档 `docs/literal-kv-astc-kernel-design.md`；本版**不声称**字面实现已完成。

## 二、五项能力分别做了什么

### 1. 该拆就拆，该合就合

新增一个“执行通道判定”：读任务文本，判断它是独立并行，还是顺序链/跨源矛盾裁决/单一最终决策/共享可变状态这类强耦合任务。

- 独立并行：可以拆给多名专家；探索重的任务先派 1 名只读侦察，回传不超过 800 字、带精确引用/产物路径的简报，其他专家复用简报。
- 强耦合/单线程：负责人任务书会明确写“不得拆给多名独立专家”，由负责人亲自执行（`direct`）或只派 1 名专家一次做完。
- 如果负责人硬要拆，平台会拒收，错误码 `DELEGATE_COUPLED_SPLIT`，并给出两条可照做的出路；不会出现“提示词说能拆、代码说不能拆”。

### 2. 子代理上下文隔离

子代理本来就有独立窗口；这一版补的是“隔离后专家仍拿得到完成任务所需的最小充分信息”，而不是把整份计划广播给每个专家。

### 3. RCR：按角色和阶段发上下文

新增角色条件路由：按“专家/负责人/规划器/核验者”和“规划/准备/执行/核验/复盘”筛选条目，再按必须/高/普通/低、相关性、预算挑选。

- 标成“必须”的条目永远不会因为预算被丢掉；预算不够时允许超出并记账。
- 被省略的条目只留下 id/ref/原因，原文仍在计划/状态/产物里，随时能取回。

### 4. Latent Brief + 缓存计量

- 把父轨迹/兄弟结论压成“硬事实 + 软摘要 + 引用”的结构化简报；同一输入复用同一份编译结果。
- 只读观察 `llm/stream` 的 usage，统计供应商真实的缓存读/写；`dsh_workplan_status` 会多一行“KV前缀缓存：调用/输入/缓存读/缓存写/命中”。
- 没有真实 usage 时不显示该行，结构化 `cache` 字段为 0，不编造命中率；只统计本进程，重启归零；可用 `DSH_WORKPLAN_CACHE_METER=0` 关闭。

### 5. ASTC 式软/硬信息压缩

- 数字、百分比、路径、哈希、编号、命令、错误码、验收编号、必须/不得这类硬事实优先逐字保留（单句≤600 字、总量≤预算；超出退精确值清单+ref）。
- 叙述性、重复性内容压成软摘要；被吸收/重复/超预算的内容只留引用。
- 依赖摘要不再“一刀切截断 800 字”，避免把唯一产物路径从中间截断；原文仍在状态里可查。

## 三、你会看到的变化

1. 负责人任务书里多一行【上下文策略】，直接告诉它“这任务该拆还是该合”。
2. 专家任务书里多一个【RCR 角色上下文包】，含验收标准、约束、依赖产物、历史教训、跨部门答复等；不再只有一句任务描述。
3. 如果负责人把跨源裁决类任务硬拆给多人，会收到 `DELEGATE_COUPLED_SPLIT` 和两条出路，而不是等到最后才发现结论对不上。
4. `dsh_workplan_status` 在真实调用后多一行 KV 前缀缓存计量（看不到这一行说明还没有 usage 数据，或计量被关闭；只统计本进程，重启归零）。

## 四、升级与回滚

升级：

```bash
dsh plugin --profile web add dsh-workplan@3.2.9
```

装完必须**手动重启一次 DSH Web**（或重新载入页面），运行中的进程才会加载新字节。

回滚：

```bash
dsh plugin --profile web add dsh-workplan@3.2.8
```

或按仓库 `RELEASING.md` 的 npm/GitHub Release 回滚流程处理。回滚不会改计划数据；3.2.9 没有改持久化 schema。

## 五、验证口径

- 类型检查：`npm run check` 通过。
- 全量测试：`npm test` → 1541 例，1540 通过 / 0 失败 / 1 todo；新增 5 个测试文件。
- 构建：`lib/` 与 `client.js` 已随源码重建；CI 会断言构建产物与源码同步。
- 运行态（用户重启后）：
  - `dsh_workplan_status` 显示 `v3.2.9` 与构建哈希；
  - 计划/派发/面板进度正常；
  - 真实模型调用后出现 KV 前缀缓存计量行；
  - 磁盘指纹与运行态指纹一致（发布记录中会给出本次指纹）。

## 六、诚实说明与已知边界

1. 第 4/5 项是插件级等价实现，不是模型内 KV/soft token；不要把它宣传成“已实现论文原方法”。
2. RCR 的预算是字符预算，不是精确 tokenizer；插件不引入 tokenizer 依赖，避免把安装包做大。
3. 耦合判定是确定性词面规则，宁可保守（不硬拆），不追求语义完美；真正的语义裁决仍由负责人/主 Agent 做。
4. 缓存计量依赖供应商返回 `cacheReadTokens/cacheWriteTokens`；不返回时如实为 0，不影响任务；无 usage 不显示该行，只统计本进程。
5. 字面 KV/ASTC 需要自建本地推理与 DSH 内核改动，见设计文档；本版不包含该部分代码。
