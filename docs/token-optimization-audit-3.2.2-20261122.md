## 1. 一句话看懂：钱花在哪里

这个插件**不直接调用部门模型**。它只在“生成计划”时直接调用一次模型（`ctx.llm.stream`），其余部门/专家都是宿主（DeepSeek Harness）拉起的子 Agent。

所以插件能省的 token 只有四类：

1. **规划器要读的输入**：任务、对话背景、规则、部门表、输出格式。
2. **规划器要写的输出**：整份计划 JSON。
3. **每个部门/专家每一步都要带的工具说明书 + 系统提示 + 任务书**。
4. **会话里反复出现的通知/结果消息**（它们会永久留在上下文里，之后每一步都重复计费）。

这次改动集中在 1、2、3，以及“结果块里重复写同一张验收表”的第 4 类输出。

## 3. 具体改了什么、为什么安全

### 3.1 规划器不再复述用户原文（最大的一块输出节省）

**旧逻辑**：规划器要在 `taskUnderstanding.originalRequest` 里把用户任务再抄一遍；平台随后又把同一段话存进 `taskAnchor`。同一段文字付了“输入 -> 输出 -> 任务书输入”三次钱。

**新逻辑**：

- `readTaskUnderstanding` 允许 `originalRequest` 缺失（`src/plan.ts:833`、`src/plan.ts:842` 一带）；
- `fillOriginalRequestFromTask` 在审计前用用户原文回填（`src/runtime.ts:1055`），正常路径和超时抢救路径都调用；
- 规划器提示词明确写“平台自动写入，不要输出该字段”（`src/plan.ts:1775` 一带）。

**安全边界**：旧计划、旧回放里已经有 `originalRequest` 的，原样保留；只有缺失才回填。审计仍能看到与用户原文一致的文本。

### 3.2 结果块不再把验收表写两遍

**旧逻辑**：模型要同时写顶层 `acceptance[{criterion,result,evidence}]` 和 `phases.verification.checks[{criterion,method,evidence}]`，校验器还会检查两者是否覆盖同一张表。

**新逻辑**：

- `synthesizeVerificationFromAcceptance`（`src/plan.ts:4596`）在缺 `checks` 时，按顶层 `acceptance` 逐条生成；
- 缺 `allPassed` 时，用 `acceptance.every(result==='pass')` 生成（有任何 unverified/fail 就是 false，保持原门禁语义）；
- 模型自己写了的 `checks/allPassed` 不覆盖；`acceptance` 为空时行为与旧版完全一样（仍然失败）。

**安全边界**：最终存进台账的仍是完整 `phases.verification`，`validateFiveStepEvidence` 和沟通格式门禁读到的结构与旧版一致；旧计划/旧回放不受影响。

### 3.3 子 Agent 任务书不再重复同一份负责人授权段

`buildLlmRulesBrief({tier:'department'})` 已经包含“review/dispatch/direct/self_effort、low 禁派、人数上下限、先配置后开工、叶子层”等全部规则。旧版在 `buildChildPrompt` 里又写了一遍，约 1,300 字符。

**新逻辑**：当真实派发带了 `llmRulesBrief` 时，`buildChildPrompt` 省略本地副本；只有旧调用方/测试传空 brief 时才保留（`src/plan.ts:7718` 一带）。

**安全边界**：没有删任何规则，只是把“同一事实源”从两份变成一份；关键串（`low/未配置...direct`、`复杂任务...`、`startPhases={...}`）仍在 brief 中逐字保留，并有回归测试钉住。

### 3.4 对话背景按需给：只付一次“最近的话”

旧版把最多 7,000 字对话塞进每个部门任务书和每次规划。大多数任务书本身已经自包含，部门 Agent 不会读那段旧寒暄。

**新逻辑**：

- 规划器：任务里有“它/这个/B/上一项”等指代 -> 保留 7,000 字；没有 -> 只带最近 3,000 字（`src/plan.ts:1775` 一带）。
- 部门任务书：真实派发传 `compactBackground: true`（`src/runtime.ts:2905`）；有指代 -> 7,000 字；没有 -> 最近 1,200 字（`src/plan.ts:7718` 一带）。
- 使用 `truncateTail` 保留“最近的”而不是“最前面的”，避免把最新对话丢掉。

**安全边界**：`buildChildPrompt` 的 `compactBackground` 默认是 `false`，直接调用方/旧测试仍是“原文不二次截断”；只有真实派发链开启。旧的 `tests/workplan-team-brief.test.ts` 因此仍通过。

### 3.5 工具说明书瘦身：每一步都少带“说明书”

工具 JSON 会随每次模型请求注入。根会话约 11 个工具，部门会话约 4 个工具。旧版 `delegate` 一份就 7,280 字符。

**新逻辑**：把重复解释、示例、已经被运行时错误码覆盖的长句压缩；保留参数名、类型、必填项、枚举、关键错误码和关键动作语义。

- `delegate` 7,280 -> 4,121
- `update` 3,471 -> 2,895
- `dispatch` 2,386 -> 2,053
- `verify` 3,426 -> 3,193

**安全边界**：没有改任何 schema 的字段名/类型/required/enum；测试 `workplan-t6-estimate-gate`（timeNotice、ESTIMATE_MISSING/ESTIMATE_INVALID）和 `workplan-251-main-deep-think`（startPhases、START_EVIDENCE_MISSING）全绿。

### 3.6 计划消息去重

计划消息里的“用户原文锚点”和 `renderPlanOutline` 的“全局任务”常常是同一段话。现在重复时只保留锚点一份（`src/plan.ts:2992`），15 任务样本省约 100 字符；用户任务越长，省得越多。

## 4. 代码/RPA 能不能替代固定流程的模型调用？

### 能，而且已经做了的部分（安全、可验证）

| 固定流程 | 旧做法 | 现在 |
|---|---|---|
| 把用户原文写进计划 | 让规划器输出 `originalRequest` | 代码从用户消息回填 |
| 生成逐项验证记录 | 让模型再抄一遍 `verification.checks` | 代码从 `acceptance` 生成 |
| 决定带多少对话背景 | 固定 7,000 字全带 | 代码按“有没有指代”选择 |
| 计划消息全局任务 | 与锚点重复 | 代码检测重复后只留一份 |
| 工具说明书 | 每个会话全量长文 | 代码按角色裁剪 + 压缩文案 |
| 状态/结果/摘要格式 | 模型自由发挥 | 代码统一渲染（原有机制） |

这些都属于“**格式、装配、去重、门禁判定**”，用代码做不会降低判断质量，反而更稳定。

### 不能安全替代的部分（这次没有动）

1. **规划器本身**：把任务拆成什么部门、几个子任务、依赖怎么设、主要矛盾是什么，是判断，不是固定流程。用模板代码替代会牺牲计划质量，也会违背“具体问题具体分析”的产品要求。
2. **部门/专家执行**：真正的搜索、读文件、改代码、验证，必须由模型做。
3. **复盘/教训内容**：`problems/detours/resolutions/prevention` 是经验总结，代码只能存，不能编。
4. **phase-0 复杂度自评**：这是用户规则要求的“子 Agent 自己判断推理等级”，不是可以静默删掉的固定流程。用代码按 `reasoningEffort` 直接继承会违反“禁止继承主 Agent 等级”的要求。
5. **通知合并/批量**：预估和完成通知可以合并，但会改变“何时让主 Agent 看到”的语义，这次没有为了省 token 而擅自改。

### 结论

**可以替代的是“固定格式与固定装配”，不能替代的是“判断与执行”。** 这次把能安全替代的部分都改成了代码；规划器、部门执行、复盘仍是模型调用，这是产品能力本身，不是浪费。

## 7. 还没有做、但值得排期的优化（避免这次改动过大）

这些不是遗漏，而是需要单独评估的行为/契约变更：

1. **规划器提示词前缀重排**：把静态规则/部门表/输出 schema 放到动态的“对话/任务”之前，让供应商的前缀缓存更容易命中。能进一步省钱，但需要真实账单对比。
2. **预估/完成通知合并**：当前每个专家预估是一条消息；可以按子任务/时间窗合并，减少主 Agent 的额外处理步数。会改变可见节奏，需产品确认。
3. **极简任务的确定性计划快路径**：对“一个动作、一个文件、一次验证”的任务，用代码生成单子任务计划，完全跳过规划器调用。省钱最多，但会失去规划器的分解/矛盾分析，需用户明确授权并做质量基准。
4. **结果块更紧凑的 wire format**（短键/单行格式）：能再省输出 token，但会动到结果契约和大量回归，风险高，暂不做。

## 8. 风险与边界（如实说明）

- 字符数不是账单金额；真实节省取决于模型 tokenizer、供应商缓存命中、任务长度和子任务数量。
- 对话背景按需截断可能让“极度依赖很久以前原话、但任务里没有任何指代”的任务少一点背景；这是本次最大的质量取舍。保留策略是：有指代就全量，没指代才只留最近 1,200/3,000 字。若真实任务出现质量回退，可把 `compactBackground` 关掉（改回 `false`）或调大上限。
- 工具说明书压缩后，模型仍能看到所有字段/枚举/必填项和错误码；如果现场发现某个长解释确实影响调用成功率，应按具体字段补回，而不是整体回滚。
- 本次没有改版本号、没有提交 git、没有发布 npm；是否发版由用户决定。

## 9. 一致性/冲突审查（本次修改 vs 原有逻辑）

结论：**在当前静态检查、完整回归与人工调用点核对范围内，没有发现未处理的逻辑冲突。** 审查中发现并已修掉 5 个真实的“边界不一致”，另有 2 个属于产品取舍而非逻辑矛盾。

### 9.1 已发现并修掉的真实不一致

1. **`originalRequest` 回填 16,000 字符，但 wire 校验上限是 8,000 字符。**
   旧规划器字段本来最多 8,000；我们第一版回填用了 `MAX_TASK_ANCHOR_CHARS`（16,000）。如果未来有任何路径重新 `validatePlan` 这份计划，会以“长度不能超过 8000”失败。
   修复：新增唯一常量 `MAX_ORIGINAL_REQUEST_CHARS = 8000`（`src/plan.ts:121`），校验与回填都用它；新增“8,000 合法 / 8,001 拒绝”的回归。

2. **“与上方用户原文相同”的去重指针，可能指向被截断的锚点。**
   计划消息和任务书里的锚点块只显示前 4,000 字；旧去重却拿完整 16,000 字锚点判断“包含”。当 `originalRequest` 超过 4,000 字时，指针会让读者以为上方有全文，但上方只显示前 4,000。
   修复：只在前 4,000 字可见锚点确实包含完整 `originalRequest` 时才去重；否则保留自己的全局任务文本（`src/plan.ts` 的 `renderPlanOutline` 与 `buildChildPrompt`）。

3. **`compactBackground` 与旧契约“完整背景不再二次截断”冲突。**
   直接调用 `buildChildPrompt` 的测试/旧代码要求原文进入；真实派发需要按需截断。
   修复：`compactBackground` 默认 `false`，只有真实派发传 `true`；旧的 `tests/workplan-team-brief.test.ts` 原样通过。

4. **“brief 非空就省略本地授权段”可能误删能力。**
   如果未来调用方传入一个非空但不是 `buildLlmRulesBrief({tier:'department'})` 的简报，本地授权段会被错误省略。
   修复：只有简报里确实包含 `部门负责人强制流程` 标记时才省略；否则 fail-open，保留本地段。并补回被压缩掉的“少走弯路”“action=status 查看进度”两句。

5. **`recentConversation` 原有“保留最近对话”的实现是头部截断。**
   它从最新消息往前收集，但最后用 `truncate` 保留开头；窗口超一行时会丢掉最新的消息。这不是本次新引入的，但会让新的“按需只带最近 1,200/3,000 字”建立在错误方向上。
   修复：`recentConversation` 改用 `truncateTail`，保留最新内容；参考探测失败时 fail-open 保留完整背景。

### 9.2 逐项核对后确认不冲突的链路

| 检查点 | 结论 | 依据/机制 |
|---|---|---|
| 旧计划/旧回放没有 `originalRequest` | 兼容 | 字段改为可选，缺失为 `''`；旧值原样保留；`reconstructFromSession` 直接读 durable，不重新按新 schema 拒绝旧计划 |
| 规划器审计 `summaryCoverage` | 不阻断 | 回填发生在 `validatePlanContext` 之前；审计仍拿用户原文比对，只是指标字段 |
| `verification.checks/allPassed` 自动生成 | 兼容 | 只补缺失；模型写了的保留；`acceptance` 为空仍失败；最终台账仍是完整 phases |
| 五步门禁/沟通格式 F3/F4/F7 | 一致 | 生成后的 `phases.verification` 结构与旧版相同；F3 仍要求 `verification` 对象，不会把“完全没写 phases”放行 |
| 计划消息去重与用户可见性 | 不冲突 | 用户原消息仍在会话；计划消息锚点最多 4,000 字；只在前 4,000 字确实包含全文时去重 |
| 工具说明书压缩 | 不冲突 | 字段名/类型/required/enum 未改；`timeNotice`、`startPhases`、`ESTIMATE_*`、`DELEGATE_*` 关键契约保留；全量工具 schema 测试通过 |
