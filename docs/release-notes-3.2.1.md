# dsh-workplan 3.2.1

## 一句话

**让干活的部门看得见兄弟已经交付了什么、让计划在派发前就点名缺掉的依赖、让失败成员的现成产物能被收编，而不是再采集/再写一遍。** 插件不直接发起模型调用；兄弟完成提示会进入负责人上下文，可能让它多处理一步，已按每人一条封顶；不改派发、验收、交付规则。

## 3.2.0 和 3.2.1 的分工

- 3.2.0 省的是「同一段文字反复付费」：交卷不再重抄开工证据、任务书截断、正文限长。
- 3.2.1 省的是「同一批事实反复采集」：兄弟部门互相可见、依赖缺口提前点名、失败成员的产物可收编、排队成员不再被误判。

## 改动前后一眼看懂

| 场景 | 3.2.0 | 3.2.1 | 说明 |
|---|---|---|---|
| 部门查进度 | 只看到自己部门的专家 | 多一个同计划兄弟索引：谁 done、产物在哪 | 最多 12 条，done 优先 |
| 兄弟完成时 | 只有主 Agent 收到通知 | 仍在跑的负责人最多收一条一行提示 | 不刷屏，完整索引走 status |
| 任务书里的已交付兄弟 | 只写计划要产什么 | 优先写实际落盘路径 | 能直接 read/grep |
| 计划依赖 | 靠规划器自觉写 dependsOn | 计划消息新增只读「依赖自检」，点名可复用前序 | 只警告，不阻断 |
| 专家失败/中断 | 只说「失败了」 | 附已落盘结算备份，或明确「未发现」 | 防止整层重写 |
| 补派新成员 | 和旧成员都显示 running | 排队中的标 `queued: true`，另有 `queuedHint` | 解决「8 行全 running、没看到新人」的误判 |

## 具体改了什么

### 1. 兄弟部门实时可见（治「不知道」）

T4 的真实事故：T3 已经交付行情/资金事实，但 T4 调 `dsh_workplan_delegate(action="status")` 时只拿到自己部门的 8 个专家，完全看不到 T3 完成到哪、产物在哪个文件；计划里 T4 的 inputs 还写着「公开政策与行业数据（待确认）」，dependsOn 只列了 T2。T4 只能自己再采集一遍。

3.2.1 起：

- status 返回 `siblingSubtasks`：同计划其他子任务，done 优先，最多 12 条，每条带状态、标题、最多 2 个已落盘产物、done 行 80 字摘要。
- 有 done 兄弟时附 `siblingHint`：先看索引，能复用就不要重复采集。
- 任务书的兄弟简报对 done 兄弟改用真实 `status.artifacts` 路径；没有登记时才退回计划产物。
- 有 done 兄弟时，任务书多一句「兄弟复用」：开工前和大阶段前先看 status。
- 子任务 done 时，仍在 running 的其他负责人最多收一条一行通知；每个负责人每个计划只发一条，避免 13 个部门互相通知产生 150+ 条常驻消息。

### 2. 依赖缺口在计划阶段点名（治「依赖少设」）

- 规划器硬规则：下游 inputs 需要行情、资金、份额、政策、行业数据等共享事实，而计划里已有专门产出该数据的子任务时，必须把它写进 dependsOn；找不到来源要写明，不能写「待确认」就派发。
- 计划消息新增只读的「依赖自检」：扫描 inputs 里的「待确认/待定/TBD/不明」等未定项，若前序存在数据型产物，点名可复用的前序 ID 并提示补 dependsOn。只警告，不自动改计划，不阻断派发。

### 3. 终止通知可收编（治「整层重写」）

- 第三层失败、外部中断、空回合、停滞、结算异常的终止通知，新增「已落盘结算备份（可先收编核验，禁止整层重写）」。
- 没有结算备份时明确写「未发现」，让负责人先确认没有可复用产物，再决定补写，不再凭印象从零重写。
- 复用已有的只读探测 `probeDelegateLandedArtifacts`，不新增写入，不改变终止判定。

### 4. 补派排队可见（治「8 行全 running、没看到新成员」）

- 并发位不够时，新成员本来就会以 `childId=null` 的占位条目排队；旧 status 把「排队」和「真的在跑」都显示成 running，负责人误以为补派失败或被重置。
- 现在 status 只给读面加 `queued: true`，并分开返回 `runningHint`（真正有会话在跑）与 `queuedHint`（排队中、不是失败、预算用完不会自动启动；再次 dispatch 会优先启动新成员，再重试 failed 旧成员）。
- 补派混合「新成员 + 上次 failed 旧成员」时，新成员优先启动；旧成员仍会重试/排队，但不会再按原顺序先占满并发位、把新人挤回队列。
- 只改读面/启动顺序，不改存储、不改门禁、不放宽并发；真正的激活仍由原派发闸和预算决定。

## 成本边界（省钱的另一面）

- 兄弟通知每条 ≤320 字，每个负责人最多一条。
- status 兄弟索引最多 12 条；team brief 仍受 1,500 字上限。
- 任务书复用规则只在有 done 兄弟时出现；计划自检只在「未定输入 + 有数据型前序」时出现。
- queued/running 拆分是读面派生字段，不新增持久化。
- 插件不直接发起模型调用；兄弟完成提示可能让负责人多处理一步，已按每人一条封顶；没有改派发规则、验收、结算、超时、并发、权限语义；补派时只调整新成员启动顺序（新成员先于旧 failed，旧成员仍重试）。

## 没有改什么（避免误解）

- 不改任务怎么拆、怎么验收、怎么交付；只调整补派时新成员的启动顺序（新成员先于旧 failed，旧成员仍重试）。
- 不给部门之间开直连通信；仍然通过主 Agent 转达 needs。
- 不自动改用户已经写好的计划依赖，只警告。
- 不因为「兄弟完成」就强迫负责人改变原方案；提示只帮助判断，不替它做决定。
- 不改旧会话回放语义。

## 怎么确认生效

1. 重新加载插件（重启 DSH，或在插件管理里禁用再启用）；插件不会自行重启。
2. 新会话里调用 `dsh_workplan_status`，返回版本应为 `v3.2.1`。
3. 源码验证：`npx tsc -p tsconfig.json --noEmit` 通过；`npm test` 应为 **1448 通过 / 0 失败 / 1 todo**（共 1449 例）。
4. 真实任务里看三处：部门 status 出现 `siblingSubtasks`；补派时新成员带 `queued: true`；失败专家的终止通知带「已落盘结算备份」或「未发现」。
