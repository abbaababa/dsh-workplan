## 二、三个缺口是什么（白话版）

已交付文件的「写保护」本来就有：用户拿到报告后，只要计划还没真正做完，
模型就不允许再动那份报告。但它有三个漏洞：

| 编号 | 漏洞 | 打个比方 |
|---|---|---|
| G1 | 只保护「主会话」，后台子 Agent 不受保护 | 门卫只认户主，保姆拿钥匙能进 |
| G2 | 只认三种写工具的名字，别的工具名根本不进检查 | 门卫只查三种工牌，换个牌子就进去了 |
| G3 | 不认符号链接，换个「捷径路径」就能绕过去 | 同一个房间有两扇门，只锁了一扇 |

## 三、新增的两个测试文件

### 1. `tests/p03-m1-write-guard-gaps.test.ts`（3 条用例）

- **基准**：绝对路径改写已交付文件 → 被拦。
- **三种写法归一**：绝对路径、`./report.md`、`sub/../report.md` → 全被拦。
- **G3**：符号链接指到同一个文件 → 与基准路径行为一致。
  真实临时目录 + 真实符号链接，不是模拟。

G3 的断言刻意写成「与基准一致」而不是写死「放行」，原因在文件头注释里：
- 缺口还在时：基准=拦、链接=放行 → 不一致 → 用例红 → 缺口被看见；
- 将来修好：两者都=拦 → 一致 → 用例转绿 → 变成「守住修复」，不用改测试。

### 2. `tests/p03-m1-guard-gating-gaps.test.ts`（2 条用例）

- **G1**：子会话改写已交付文件不被拦；并用根会话作对照，证明差别只来自
  `isRootSession` 那个分支。既有用例
  `tests/workplan-presented-write-guard.test.ts:184` 已经把「非根会话放行」
  当作契约钉住，所以真正修复必须连它一起改 —— 这属于产品决策，归 M3。
- **G2**：`apply_patch` 这类第四个写工具名不进闸门；同时用 `read` /
  `present` / `dsh_workplan_dispatch` 作对照，证明不是闸门整体失灵，只是
  工具名清单没覆盖。
